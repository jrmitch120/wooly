# Browser-based OAuth as the primary auth flow; manual token entry as the headless fallback

Connecting a profile to a Mastodon account needs an authentication flow. We use browser-based OAuth as the primary path, since it's the flow Mastodon instances expect and never exposes a password to the client. For headless environments where a browser redirect isn't possible, we fall back to manually pasting an access token obtained out-of-band. Password-grant authentication (username/password directly to the client) is explicitly ruled out.

**The redirect comes back to a loopback socket this client opens for the length of one sign-in** (#20). A terminal client has no web address to be redirected to, so it borrows one: a socket bound to `127.0.0.1` on whatever port the OS has free, spoken to over enough hand-written HTTP to answer a browser with one sentence. A fixed port would collide with whatever else is on the machine, including a second copy of this client. Because the redirect URI carries that port and an instance holds a registration to the URI it was registered with, the app registration cannot be cached and reused across sign-ins — each `profile add` registers again, leaving one application entry per sign-in on the instance. That is the price of not owning a port, and connecting a profile is rare enough to pay it.

Nothing else on the machine is stopped from reaching that socket, so the authorization request carries a random `state` value, and a redirect arriving without it is ignored — not spent, and not treated as an answer either. Ending the sign-in on one would hand any local process a way to stop a sign-in by guessing a port; ignoring it costs only the wait already being served. The same ordering governs what the user is told: an instance's refusal is text the instance chose, and anything that can reach the socket could have chosen it instead, so it is repeated back only once the state says the instance is who said it. PKCE would be the stronger answer, but Mastonet's `ConnectWithCode` has no way to send a code verifier, so it is not available without going around the API client — which ADR-0001 chose precisely to avoid.

**Which path a machine gets is decided by whether there is a terminal, not by whether there is a browser** (#20). A browser sign-in is a conversation held in the terminal — the address is printed there, and the outcome is reported there — so with no terminal to hold it, `profile add` refuses at once and names `--token`, rather than opening nothing and waiting out its patience on a browser that was never going to answer. A terminal with no browser is the other way round and stays on the primary path: the address is printed, and a user who can read it can finish the sign-in from another machine.

## Consequences

Ruling out password grant means there is no "just type your password" path, even though users may expect one from other CLI tools — this is deliberate, not an oversight, since it would mean handling and potentially mishandling account passwords directly.

Because the two paths differ only in how the access token is come by, a profile records nothing about which one made it. That is what keeps storage, verification, and every later command identical for both — but it also means a token cannot later be traced back to the flow that issued it, and re-authenticating a profile is always a fresh choice rather than a repeat of the last one.
